# CloudFile 单库千万条目性能目标（研发验收口径）

> 状态：**研发目标，尚未通过 1000 万条目真实压测，不属于当前产品性能承诺**。
> 基线：CloudFile V2 / Seafile CE14；本文件不调整数据库 Schema、物理存储格式或 CE 同步上限。

## 目标

单个资料库（Repo）包含 **1000 万文件与目录条目**时，仍具有良好的 **交互、授权搜索与并发写入**性能；
并且一个大库的导入、GC、重建索引、批量读写不应让同一部署的其他库明显失去响应。
“可以存下 1000 万条目”本身不算达标。

## 四类最小验收负载

1. **均衡目录**：约 1 万个目录，每个约 1000 个直接子项，总计约 1000 万条目。
2. **真实热点目录**：总量 1000 万，包含 8000 项直接子目录；验证单页 200 项和按需树展开。
3. **极端目录（找拐点，不预设必须通过）**：直接子项达到 10 万的单目录；检查 SeafDir 完整解压/解析、内存及目录修改放大。
4. **多库隔离**：一个 1000 万库持续批量上传、索引或 GC，同时另一个库执行分页、搜索和小文件读写；对比同条件空闲基线。

每类负载覆盖实际中文文件名、长路径、目录 ACL/共享根、原生 Tag、不同文件大小、历史版本、多个用户；
不要仅用 1000 万个空文件证明容量。

## 性能与正确性指标

- **交互**：EAP/Hub 分页与懒加载，200 项一页；记录 P50/P95/P99、SQL 次数、完整目录解压/解析次数、CPU/RSS、HTTP 响应大小。200 项分页 P95 小于 1 秒仅为初步测量目标，需根据环境实测校准。
- **搜索**：完整初始索引、增量追赶、跨目录/Tag 搜索、准确的 ACL/共享权限、索引延迟以及范围分页；不能以跳过受控子树的搜索结果宣称能力完成。
- **写入**：多目录并发上传/修改、CAS/Branch 冲突重试、提交等待与尾延迟、历史版本/Guard 正确性；不能用降低授权或丢失提交换速度。
- **多库**：对比普通库在大库负载前后的延迟/错误率，同时记录共享 DB 连接、IOPS、CPU、内存、Redis 和搜索工作线程；优化限制后台资源争用，而不是额外部署一套库级服务。
- **运维**：GC、fsck、历史处理与初始索引必须避免无限制内存增长及长时间饥饿交互操作。

## 设计边界和交付顺序

1. **已发现的路径**：C/Go 本地对象访问重复查存储路由。先做 repo_id 级、有界进程内物理路由缓存；不缓存权限与文件内容。此项见同分支 `cf-v2-storage.c` 和 Go `cf_v2_storage.go`。
2. **已存在的机制**：Hub 的有界 ACL 分页与 EAP 的按需分页继续复用，不恢复整层拉取兜底。再验证底层 SeafDir 是否仍完整解压和解析单目录对象。
3. **待量化**：Branch 竞争与批量写入、Meilisearch 增量/权限完整性、GC/索引任务对其他资料库的影响；每项以真实负载数据和独立小 PR 收敛。

默认不做数据库改表/分库、全量文件 SQL 索引、第二套树元数据、Redis 目录全量缓存、对象格式重写、
每库微服务或新配置开关。单库服务端 1000 万条目目标**不等于**所有文件必须支持客户端全量同步。
